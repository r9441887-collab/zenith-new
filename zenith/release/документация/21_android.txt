# Android (app android)

Zenith компилирует нативные 64-битные приложения для **Android 11, 12 и 13
(`arm64-v8a`)**. Выход — статический ELF64, который Android запускает
напрямую: без `libc`, без динамического линкера, без NDK.

Программа обращается к ядру напрямую через `svc #0` (Linux-системные
вызовы AArch64). Никаких внешних тулчейнов не требуется — компилятор сам
кодирует все инструкции.

## Тип приложения

```zenith
app android
    api_level: 30      # необязательно (Android 11 = 30, 12 = 31, 13 = 33)
    min_sdk: 21        # необязательно (минимальный уровень устройства)
    label: myapp       # необязательно (метка)
```

| Директива | Значение | По умолчанию |
|-----------|----------|--------------|
| `api_level:` | Уровень API, под который написана программа (записывается в `.note.android.ident`) | `30` |
| `min_sdk:` | Минимальный уровень API, на котором программа разрешена запускаться | `21` |
| `label:` | Произвольная метка | пусто |

Поддерживаемые версии — одна строка `app android`, различается только
уровень API:

| Android | `api_level:` |
|---------|--------------|
| 11 | `30` |
| 12 | `31` |
| 13 | `33` |

Код при этом не разветвляется: и 11, и 12, и 13 используют один и тот же
набор Linux-системных вызовов AArch64, поэтому смена `api_level` меняет
только значение в `.note.android.ident` (поле `NT_VERSION` = `r30`,
`r31` или `r33`).

Ограничения (проверяются компилятором):

- `api_level >= 21` и `min_sdk >= 21` — именно с Android 5.0 (API 21)
  появился 64-битный `arm64-v8a`;
- `min_sdk <= api_level`;
- архитектура `arm64-v8a` выбирается автоматически, отдельная директива
  не нужна.

## Сборка и запуск

```bash
zenith app.z -o app.elf
```

Полученный файл — статический ELF. На устройстве:

```bash
adb push app.elf /data/local/tmp/app.elf
adb shell chmod 755 /data/local/tmp/app.elf
adb shell /data/local/tmp/app.elf
```

Запуск идёт от отдельного процесса (`execve`), поэтому программа
завершается сама — `main` может просто вернуть код возврата.

Точка входа — `func main()` (либо первая функция, если `main` нет).
Код возврата `main` становится кодом завершения процесса, поэтому
`return 1` действительно даст exit status 1.

## Структура ELF

| Часть | Содержимое |
|-------|------------|
| `PT_NOTE` | `.note.android.ident` с `NT_VERSION` = `r<api_level>` |
| `PT_LOAD` (R+X) | ELF-заголовки, рантайм-помощники, функции, строки |
| `PT_LOAD` (R+W) | глобальные переменные |
| `PT_GNU_STACK` | Неисполняемый стек |

Намеренно **нет** `PT_INTERP` и `PT_DYNAMIC`: Android не запускает
`/system/bin/linker64`, ядро грузит образ сам. `e_entry` указывает на
`_start`, который выставляет `sp`, читает `argc` из `[sp]` и передаёт
управление в `main`, после чего завершает процесс.

Адрес загрузки по умолчанию — `0x400000` (тот же базовый адрес линейки
`app linux`).

## Вывод текста

`print()` / `println()` пишут в файловый дескриптор `1` (stdout) через
системный вызов `write`. Перевод строки — `\n`. Числа печатаются со
знаком, целыми.

## Встроенные функции

| Функция | Описание |
|---------|----------|
| `print(x)` | Вывести строку / целое / символ в stdout |
| `println(x)` | То же, но с переводом строки |
| `alloc(size)` | Выделить память (страница + заголовок), вернуть указатель или `0` |
| `free(ptr)` | Освободить память, выделенную `alloc()` |
| `exit(code)` | Завершить процесс с кодом |
| `sleep(ms)` / `delay_ms(ms)` | Задержка через `nanosleep` |
| `delay_us(us)` | Задержка с микросекундным разрешением |
| `millis()` | Миллисекунды монотонных часов |
| `micros()` | Микросекунды монотонных часов |
| `rdtsc()` | "Счётчик тактов" — на этом таргете тоже наносекунды |
| `getpid()` | Идентификатор процесса |
| `argc()` | Число аргументов командной строки |
| `abs(x)` | Модуль числа |
| `min(a, b)` / `max(a, b)` | Минимум / максимум |
| `clamp(x, lo, hi)` | Ограничить `x` диапазоном `[lo; hi]` |
| `str_len("text")` | Длина строки в байтах |

`gpio_*` и `led_*` на этом таргете не имеют эффекта (компилятор выдаёт
предупреждение) — у обычного Android-устройства нет такого MMIO.

## Файлы, память и энтропия

Отдельный набор встроенных функций работает поверх тех же `svc #0` и
доступен на 11, 12 и 13 одинаково.

| Функция | Системный вызов | Описание |
|---------|-----------------|----------|
| `file_open(path, flags)` | `openat(AT_FDCWD, …)` | Открыть файл, вернуть дескриптор или `0` |
| `file_read(fd, buf, len)` | `read(2)` | Прочитать до `len` байт, вернуть их число или `0` |
| `file_write(fd, buf, len)` | `write(2)` | Записать `len` байт, вернуть их число или `0` |
| `file_pread(fd, buf, len, off)` | `pread64(2)` | Прочитать из `off`, не двигая позицию |
| `file_close(fd)` | `close(2)` | `1` при успехе, `0` при ошибке |
| `file_size(path)` | `statx(2)` | Размер файла в байтах или `0` |
| `random_bytes(buf, len)` | `getrandom(2)` | Заполнить буфер случайными байтами, вернуть их число |
| `memfd_create(name)` | `memfd_create(2)` | Анонимный файл в памяти, вернуть дескриптор или `0` |

### Файловые вызовы по дескриптору и по пути

| Функция | Системный вызов | Описание |
|---------|-----------------|----------|
| `file_lseek(fd, off, whence)` | `lseek(2)` | Сдвинуть позицию, вернуть новую или `0` |
| `file_pwrite(fd, buf, len, off)` | `pwrite64(2)` | Записать по смещению, не двигая позицию |
| `file_truncate(fd, len)` | `ftruncate(2)` | Обрезать файл до `len` байт, `1` при успехе |
| `file_fsync(fd)` | `fsync(2)` | Сбросить на диск, `1` при успехе |
| `file_fstat_size(fd)` | `lseek(2)` | Размер открытого файла, позиция восстанавливается |
| `file_unlink(path)` | `unlinkat(2)` | Удалить файл, `1` при успехе |
| `file_rename(old, new)` | `renameat(2)` | Переименовать, `1` при успехе |
| `file_mkdir(path, mode)` | `mkdirat(2)` | Создать каталог, `1` при успехе |

`whence` в `file_lseek` — обычное число: `0` — `SEEK_SET`, `1` — `SEEK_CUR`,
`2` — `SEEK_END`.

`file_fstat_size` сознательно сделан на `lseek(fd, 0, SEEK_END)`, а не на
`fstat(2)`: у `fstat` смещение `st_size` различается между ABI, а лишний
128-байтный буфер на кадре стека здесь ни к чему. Смещение дескриптора
сохраняется и возвращается обратно, поэтому вызов ничего не меняет, кроме
результата.

`file_unlink` удаляет только файлы. `unlinkat` с флагом `AT_REMOVEDIR` не
используется, поэтому удалить каталог этим вызовом нельзя — для каталогов
есть только `file_mkdir`.

### Память и отображения

| Функция | Системный вызов | Описание |
|---------|-----------------|----------|
| `mem_copy(dst, src, len)` | — | Копирование с семантикой `memmove`, вернуть `len` |
| `mem_set(ptr, byte, len)` | — | Заполнить байтом, вернуть `len` |
| `mem_cmp(a, b, len)` | — | `0` если равны, иначе разность первых различающихся байт |
| `mmap(len, prot, flags)` | `mmap(2)` | Анонимное отображение, вернуть адрес или `0` |
| `munmap(addr, len)` | `munmap(2)` | Снять отображение, `1` при успехе |
| `madvise(addr, len, how)` | `madvise(2)` | Подсказка ядру, `1` при успехе |

- `mem_copy` корректно обрабатывает пересечение областей: если `dst` выше
  `src`, копирование идёт с конца, иначе — с начала.
- Длина `0` и отрицательная длина во всех трёх функциях дают `0` и ничего не
  делают. Отрицательная длина отвергается явно, а не считается «ненулевой»:
  цикл, считающий до нуля, иначе крутился бы, не останавливаясь.
- `mem_cmp` возвращает разность **первого** различающегося байта, поэтому
  знак совпадает с `memcmp(3)`: `0` — равны, `< 0` — `a` меньше `b`.
- `mmap` не принимает ни дескриптора, ни смещения: только анонимные
  отображения. Соответствующие регистры `fd` и `offset` принудительно
  обнуляются, иначе `MAP_ANONYMOUS` падал бы с `EINVAL`.
- Константы для `mmap` передаются числами: `PROT_READ` = `1`,
  `PROT_WRITE` = `2`, `MAP_PRIVATE` = `2`, `MAP_ANONYMOUS` = `32`,
  `MADV_NORMAL` = `0`, `MADV_DONTNEED` = `4`. Анонимное отображение для
  чтения и записи — `mmap(8192, 1 + 2, 2 + 32)`.

### Сведения о системе, аргументы и окружение

| Функция | Системный вызов | Описание |
|---------|-----------------|----------|
| `getuid()` | `getuid(2)` | Идентификатор пользователя, **как есть** |
| `geteuid()` | `geteuid(2)` | Эффективный идентификатор пользователя |
| `getgid()` | `getgid(2)` | Идентификатор группы |
| `sys_uname_field(buf, len, which)` | `uname(2)` | Одно поле `utsname`, вернуть длину или `0` |
| `sys_page_size()` | — | Размер страницы, сейчас всегда `4096` |
| `sys_sched_yield()` | `sched_yield(2)` | Уступить планировщик, `1` при успехе |
| `sys_exit_group(code)` | `exit_group(2)` | Завершить всю группу потоков |
| `arg_get(index, buf, len)` | — | Скопировать `argv[index]`, вернуть длину или `0` |
| `env_get(name, buf, len)` | — | Скопировать значение переменной окружения |

- `sys_uname_field` берёт поле по номеру `0..5`: `sysname`, `nodename`,
  `release`, `version`, `machine`, `domainname`. Каждое поле — 65 байт, и
  `len` — это размер буфера, а не длина строки. В `buf` попадает ровно
  `strlen(поля) + 1` байт вместе с завершающим нулём. Номер вне `0..5` и
  слишком маленький буфер дают `0`.
- `getuid` / `geteuid` / `getgid` возвращают сырое значение: **`0` там —
  законный идентификатор**, а не признак ошибки. Проверить вызов можно
  только косвенно.
- `sys_page_size` возвращает константу `4096`. На устройствах со страницей
  16 КБ это значение будет неверным — определить размер страницы из
  пользовательского режима без `auxv` нельзя.
- `env_get` возвращает **значение**, то есть то, что после `=`; если у
  переменной нет `=` или её нет в окружении, результат `0`.
- `arg_get` и `env_get` читают исходный блок стека ядра, который
  `argv`/`envp` занимают прямо в нём, поэтому копирование не требует ни
  `libc`, ни дополнительных системных вызовов.
- `sys_exit_group` не возвращает управления.

### Флаги `file_open`

Флаг — обычное число, константы передаются как есть:

| Константа | Значение | Смысл |
|-----------|----------|-------|
| `O_RDONLY` | `0` | Только чтение |
| `O_WRONLY` | `1` | Только запись |
| `O_RDWR` | `2` | Чтение и запись |
| `O_CREAT` | `64` | Создать файл, если его нет |
| `O_TRUNC` | `512` | Очистить существующий файл |
| `O_APPEND` | `1024` | Писать в конец файла |
| `MFD_CLOEXEC` | `1` | Флаг по умолчанию в `memfd_create` |

### Соглашение об ошибках

Все эти функции возвращают **`0` при ошибке**, а не отрицательный код
`errno`: значение `-errno` из ядра превращается в ноль на границе
встроенной функции.

- `file_read` / `file_write` / `file_pread` / `random_bytes` возвращают
  число реально прочитанных или записанных байт, поэтому `0` означает и
  ошибку, и конец файла — различать надо по контексту.
- `file_size` возвращает `0` и для пустого файла, и для недоступного пути.
  Полезный размер всегда неотрицателен, поэтому других признаков нет.
- `file_close` — единственная из них, кто возвращает **`1` при успехе**:
  у `close(2)` ноль означает именно успех, и «ноль = ошибка» пришлось бы
  инвертировать. Так же поступают и остальные вызовы, у которых
  успешный результат явно равен нулю: `file_truncate`, `file_fsync`,
  `file_unlink`, `file_rename`, `file_mkdir`, `munmap`, `madvise`,
  `sys_sched_yield`. У них в ядре `0` и есть успех, а `1` удобнее
  совпадает с остальными, у которых успех — ненулевое число.
- `mmap` возвращает адрес отображения, который ненулевой всегда, так что
  проверять надо именно на `0`.
- Исключение из правила — `getuid` / `geteuid` / `getgid`: они возвращают
  сырое значение, где `0` означает корень, а не ошибку.

### Требования к уровню API

Все вызовы выше доступны на Android 11 и новее:

| Вызов | Появился в API | |
|-------|----------------|---|
| `pread64`, `read`, `write`, `close`, `openat` | раньше 21 | доступны везде |
| `lseek`, `ftruncate`, `fsync`, `unlinkat`, `renameat`, `mkdirat` | раньше 21 | доступны везде |
| `pwrite64` | ранний ARM64 | доступен |
| `uname`, `getuid`, `geteuid`, `getgid` | раньше 21 | доступны везде |
| `sched_yield`, `exit_group` | раньше 21 | доступны везде |
| `madvise` | 21 | доступен |
| `mmap`, `munmap` | раньше 21 | доступны везде |
| `getrandom` | 28 | доступен |
| `memfd_create`, `statx` | 30 | доступны на 11/12/13 |

`statx` появился в API 30 — на 11, 12 и 13 он есть, поэтому `file_size()`
не нуждается в запасном варианте через `open` + `lseek`. Именно поэтому
`file_fstat_size` сделан на `lseek`: он работает и на API 21.

> Ограничения проверяющей среды: `qemu-aarch64-static` версии 7.2 не
> знает системный вызов 332 (`statx`) и печатает `Unknown syscall 332`,
> поэтому под ним `file_size()` вернёт `0`. На настоящем устройстве и на
> более свежем QEMU вызов работает — это ограничение эмулятора, а не кода.
> Тот же эмулятор не выполняет `ftruncate` (77) и `fstat` (80) для
> гостя-`aarch64`, поэтому `file_truncate()` под ним возвращает `0` и
> `file_fstat_size()` проверен на реальном файле через `lseek`. Ещё он
> путает номера 166, 167 и 168 (`getuid`, `geteuid`, `getgid`) с другими
> вызовами и печатает для них чужие значения, так что идентификаторы
> пользователя проверять нужно на устройстве.

### Пример

```zenith
app android
    api_level: 33      # Android 13

func main() -> int
    # анонимный файл в памяти: не нужен ни каталог, ни права
    var fd: int = memfd_create("zenith-demo")
    if fd == 0
        println("memfd_create failed")
        return 1
    end

    if file_write(fd, "0123456789", 10) == 10
        var buf: int = alloc(16)
        file_pread(fd, buf, 4, 2)      # читаем "2345" со смещения 2
        file_close(fd)
        free(buf)
        println("ok")
    end

    if file_size("/data/local/tmp/nothing") != 0
        println("unexpected")
    end
    return 0
end
```

## Память

`alloc(size)` выделяет через `mmap(MAP_ANONYMOUS|MAP_PRIVATE)`, округляя
размер вверх до страницы. Анонимный маппинг обнулён ядром, поэтому
`alloc()` заодно заменяет `calloc()`. В первых 16 байтах блока хранится
округлённая длина — по ней `free()` понимает, сколько байт снимать, и
возвращает страницы ядру целиком. Указатель, который получает программа,
выровнен по 16 байт (максимальное естественное выравнивание AArch64).

## Модель данных

- **LP64**: глобальные переменные, локальные и параметры занимают по
  8 байт и читаются/пишутся полным 64-битным регистром. Это нужно, чтобы
  64-битный указатель из `alloc()` не обрезался, когда его кладут в
  переменную типа `int`.
- `int`, `float`, `bool` занимают 4 байта, но слоты выровнены по 8.
  **Вещественные числа не поддерживаются** (как и в `app arm64`):
  компилятор печатает диагностику («float literals are not supported yet»
  и т. п.), но **продолжает сборку** — вещественное значение при этом не
  вычисляется. Если программе нужна арифметика с дробными числами, считайте
  целые (например, тысячные доли) либо ждите появления поддержки float.
- Структуры: каждое поле выровнено по 8 байт, итоговый размер тоже
  кратен 8 (настоящий LP64-layout, а не 4-байтовый, как в `app arm64`).
- Строки — 64-битные указатели на байты в сегменте данных (тоже, как в
  других таргетах). `print()`/`println()` понимают строковый литерал или
  целое число; переменная типа `string` — это указатель, поэтому
  `print(s)` напечатает адрес, а не текст. Это общее поведение Zenith
  (см. `07_вывод_в_консоль.txt`), а не особенность Android.
- Массивы, глобальные переменные, вложенные циклы и ветвления —
  поддерживаются.
- Аргументы функций — в регистрах `x0..x7` (до 8), результат в `x0`;
  локальные переменные живут в кадре вызываемого; `sp` выровнен по
  16 байт.

## Ограничения

- Только `arm64-v8a`. 32-битные ABI (`armeabi-v7a`) не поддерживаются.
- Нет вещественных чисел, `string` как отдельного типа и сети. Файловый
  ввод-вывод есть (см. «Файлы, память и энтропия»), но это только
  дескрипторы и байты: `fopen`-подобного режима, `printf` и поиска по
  каталогам нет. Любой недостающий вызов добавляется поверх `svc #0`.
- Смешивание с C/C++ (`--cc` / `--cxx`) пока не поддерживается: готовые
  объекты собраны под glibc, а Android использует Bionic. Компилятор
  выдаёт понятную ошибку вместо тихой поломки.
- `argc()` по-прежнему даёт только счётчик, а сами строки лежат на стеке
  ядра и недоступны напрямую. Чтобы их прочитать, нужно явно скопировать
  нужную строку через `arg_get(index, buf, len)` — это единственный
  поддерживаемый способ, и он ничего не выделяет.

## Пример

```zenith
app android
    api_level: 30
    min_sdk: 21

func main() -> int
    println("Zenith on Android 11")

    var buf: int = alloc(1024)
    if buf != 0
        free(buf)
        println("allocated and released")
    end

    sleep(100)
    return 0
end
```

Сборка и проверка:

```bash
zenith app.z -o app.elf
file app.elf            # ELF 64-bit LSB executable, ARM aarch64, statically linked
readelf -hlW app.elf    # нет INTERP и DYNAMIC — образ запускается сам
```

## Проверка

В репозитории лежит самопроверяющаяся программа
`tools/android_smoke.z`: она печатает `ALL PASS` и возвращает `0` только
если все утверждения выполнены (арифметика, строки, циклы, `switch`,
указатели LP64, `alloc`/`free`, сравнения, `sleep`/`delay_us`,
`micros`/`millis`, `getpid`, `memfd_create` + `file_write` + `file_pread` +
`file_close`, `random_bytes`, а также `0` вместо дескриптора и размера для
несуществующего пути).

Проверено на всех трёх уровнях — меняется только строка `api_level`:

```bash
for api in 30 31 33; do
  sed "s/^\( *\)api_level: .*/\1api_level: $api/" tools/android_smoke.z > /tmp/smoke.z
  zenith /tmp/smoke.z -o /tmp/smoke.elf
  chmod +x /tmp/smoke.elf
  echo -n "api $api: "; qemu-aarch64-static /tmp/smoke.elf | tail -1
done
# api 30: ALL PASS
# api 31: ALL PASS
# api 33: ALL PASS
```

```bash
zenith tools/android_smoke.z -o smoke.elf
chmod +x smoke.elf

# на устройстве:
adb push smoke.elf /data/local/tmp/smoke
adb shell chmod 755 /data/local/tmp/smoke
adb shell /data/local/tmp/smoke; echo "exit=$?"   # ожидается ALL PASS, exit=0

# без устройства — user-mode эмуляция (работает, т.к. образ статический):
qemu-aarch64-static ./smoke.elf; echo "exit=$?"
```

Ненулевой код возврата означает, что первая несошедшаяся проверка
напечатает `FAIL: ...`, и номер утверждения будет виден в выводе.
